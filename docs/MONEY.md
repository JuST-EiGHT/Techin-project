# Деньги: банки, ДДС, платёжный календарь, главный дашборд

Зачем: P&L по отчётам Ozon показывает, сколько заработано. Но продавцу так же важно,
сколько денег реально на счетах, когда придёт следующая выплата Ozon, какие траты
впереди и не будет ли кассового разрыва. Этим занимаются сервисы управленческого учёта —
ориентир для нас КУБ24.ФинДиректор. Здесь — что умеет КУБ24, что берём, как устроим и
по каким шагам делаем.

**Сервис универсальный.** Никаких данных конкретного продавца в коде и логике: банки,
статьи, налоговый режим, график выплат, условия оплаты поставщикам — настройки
пользователя с разумными шаблонами по умолчанию.

## 1. Что умеет КУБ24 (исследование, октябрь 2026)

Сайт kub-24.ru из облачной среды разработки не открывается — сведения собраны из
открытых обзоров и страниц КУБ24 в поиске; детали стоит перепроверить.

| Возможность | Как в КУБ24 |
|---|---|
| Загрузка выписок из банков | автоматически по интеграциям с банками (в обзорах: Сбер, Т-Банк, Альфа, Точка, Модульбанк, Blanc); из остальных банков — выписка по e-mail / файлом |
| Отправка платежей | через ту же интеграцию с банком можно отправлять исходящие платежи |
| Авторазнесение | операции автоматически разносятся по статьям ДДС и проектам по правилам; статьи настраиваются под отрасль |
| ДДС | отчёт о движении денег прямым (кассовым) методом, график денежных потоков, остатки на счетах, движение по направлениям и проектам, топ покупателей и поставщиков |
| Кассовые разрывы | прогноз кассового разрыва |
| Платёжный календарь | план-факт; перенос платежа сразу пересчитывает прогноз |
| ОПиУ | отчёт о прибылях и убытках; для селлеров — по каналам продаж (Ozon, WB, свой сайт) |
| Прочее | дебиторка и кредиторка, бюджеты БДР/БДДС, 50+ отчётов, дашборды, права доступа сотрудников, 20+ интеграций (1С, банки), счета/акты/УПД |
| Маркетплейсы | КУБ24 подчёркивает: маркетплейс платит по своему графику, поэтому селлеру нужен ДДС, а не только ОПиУ. Прямой загрузки данных Ozon/WB по API в открытых источниках не нашли |

## 2. Что берём и чем отличаемся

**Берём:** автоматическую загрузку операций из банков, статьи ДДС с автоправилами,
ДДС и остатки на счетах, платёжный календарь с прогнозом кассового разрыва, главный
дашборд собственника.

**Наше преимущество:** мы уже знаем, что Ozon должен выплатить (начисления по API и
XLSX, баланс Ozon), и видим, что реально пришло на счёт. Значит, можем:
- сверять выплаты Ozon с поступлениями на расчётный счёт и ловить расхождения;
- прогнозировать следующую выплату Ozon в платёжном календаре без ручного ввода;
- показывать на одном экране: продано на Ozon → начислено → выплачено → пришло на счёт.

**Не делаем (пока):**
- отправку платежей из сервиса — только чтение выписок. Если когда-нибудь понадобится —
  отдельный шаг с правилами безопасности как для цен (dry-run → подтверждение → аудит);
- счета, акты, УПД и бухгалтерию — сервис остаётся управленческим учётом;
- бюджеты БДР/БДДС и права сотрудников — после запуска, по запросу пользователей.

## 3. Источники данных о деньгах

| Источник | Что даёт | Как |
|---|---|---|
| Банк по API | операции и остатки по расчётным счетам, автообновление | коннектор на каждый банк (см. §4), Celery по расписанию |
| Выписка файлом | то же для любого банка без API и для истории глубже, чем отдаёт API | формат обмена с 1С (`1CClientBankExchange`, обычно windows-1251) — его выгружает любой интернет-банк |
| Ozon API, баланс | входящий и исходящий баланс у Ozon, начислено, выплаты за период (≤ 30 дней) | `POST /v1/finance/balance` (бета, «Финансы → Баланс») |
| Ozon API, финансовый отчёт | итоги по полумесячным периодам с выплатами | `POST /v1/finance/cash-flow-statement/list` |
| Начисления Ozon | что начислено по дням (шаги 1.4, 2.2) | уже есть |

Методы Ozon перед реализацией сверить с `docs/ozon/seller_api_2026-10.txt` (правило 10).

## 4. Банки по API

Общий интерфейс `BankProvider` (как `CostProvider` у парсеров): проверить доступ,
список счетов, операции за период, остатки. Новый банк — новая реализация, остальной код
не меняется. Токены банков хранятся как ключи Ozon: только Fernet-шифротекст, не
логируются и не возвращаются (правило 7). Запрашиваем только права на чтение выписок.

| Банк | Что известно | Когда |
|---|---|---|
| Т-Банк | T-API: `GET business.tbank.ru/openapi/api/v1/bank-statement`, Bearer-токен выпускает сам клиент в кабинете Т-Бизнеса (доступ `bank-statements/get`); 10 запросов/с; данные с июня 2023; до 50 000 операций за запрос; вебхуки — по запросу в банк | шаг 3.7 |
| Точка | спецификация в репозитории — `docs/banks/TOCHKA.md` (выжимка) и `docs/banks/tochka/`: OAuth 2.0 + разрешения (consents), выписка асинхронно (заказать → дождаться `Ready`), остатки, вебхуки о платежах; песочница есть | шаг 3.7 |
| Модульбанк | по открытым источникам не подтверждено — проверить документацию при реализации | шаг 3.7, если API доступен клиенту |
| Сбер | СберБизнес API: токены из кабинета, сертификат электронной подписи (первичный — в отделении), для платформ — партнёрская авторизация СберБизнес ID | шаг 8.5 |
| Альфа, ВТБ и др. | открытого API выписки для малого бизнеса в открытых источниках не нашли; вероятно, только партнёрские программы | шаг 8.5; до тех пор — выписка файлом |

Порядок: сначала банки, где токен выдаёт сам клиент (подключение за минуты, без
договора с банком), затем — банки, где сервису нужно стать партнёром (договор, юрлицо,
сертификаты): это задача запуска (фаза 8). Для всех банков работает загрузка файлом.

## 5. Модель данных (набросок для шагов 3.6–3.10)

- `bank_connections` — подключение к банку: провайдер, зашифрованный токен, статус,
  срок, последняя синхронизация.
- `bank_accounts` — расчётные счета пользователя: банк, номер, валюта, источник (api | file).
- `bank_transactions` — операции: дата, сумма (+ приход / − расход), контрагент и ИНН,
  назначение платежа, банковский идентификатор операции, источник, сырой ответ.
  Исходные данные (правило 12): не удаляются и не перезаписываются; повторная загрузка
  того же периода из API или файла не создаёт дублей (ключ — идентификатор операции банка,
  для файла — номер + дата + сумма + счёт).
- `bank_balances` — остатки на дату (снимки).
- `cash_categories` — статьи ДДС пользователя (шаблон селлера по умолчанию: поступления
  от маркетплейсов, закупка товара, логистика и фулфилмент, реклама, налоги, зарплата,
  аренда, банк и эквайринг, перевод между своими счетами, прочее).
- `categorization_rules` — правила разнесения: ИНН/название контрагента, слова в
  назначении, направление и сумма → статья. Ручная разметка операции важнее правила;
  из ручной разметки сервис предлагает новое правило.
- `planned_payments` — платёжный календарь: разовые и повторяющиеся платежи и поступления,
  связь с фактической операцией (план-факт).

Поступления от маркетплейсов распознаются по ИНН плательщика (Ozon — ООО «Интернет
Решения», ИНН 7704217370, указан в отчёте о реализации); список ИНН маркетплейсов —
справочник, а не код.

## 6. Платёжный календарь — откуда берутся будущие траты

Всё — настройки пользователя, без зашитых условий конкретного магазина:
- **выплаты Ozon** — прогноз по балансу Ozon и графику выплат (график — настройка,
  по умолчанию стандартный график Ozon; сверить с актуальными условиями Ozon);
- **регулярные платежи** — аренда, зарплата, подписки, кредиты: сумма, периодичность, день;
- **оплата поставщикам** — шаблоны на выбор: по факту продаж (себестоимость проданного ×
  НДС, раз в неделю / месяц), предоплата партии, отсрочка N дней после поставки;
- **налоги** — по налоговому профилю пользователя (ИП / ООО, система налогообложения, НДС —
  шаг 2.5, docs/TAXES.md): суммы и сроки уплаты;
- **разовые платежи** — вручную.

Прогноз остатка = текущий остаток на счетах + плановые поступления − плановые платежи;
день, где прогноз уходит ниже нуля (или порога пользователя), — кассовый разрыв.

## 7. Главный дашборд (`/dashboard`)

Цифры сверху: остаток на счетах, у Ozon на балансе (к выплате), продано за период,
прибыль и маржа за период (P&L), ближайший кассовый разрыв (если есть).

Графики (Recharts, без графиков ради графиков):
- выручка на Ozon по дням / неделям — с прошлым периодом для сравнения;
- деньги: пришло на счёт от Ozon и других, ушло по статьям — по неделям;
- прогноз остатка на 30/60/90 дней с плановыми платежами и выплатами Ozon;
- ближайшие платежи и поступления — список на 14 дней.

Выбор периода и источника (XLSX / API), бейдж источника как на странице финансов.
Виджеты следующих фаз (остатки — 5.1, изменения цен — 6.4, аномалии — 7.2) добавляются
на главную в своих шагах.
