# Выплаты Ozon и планирование денег

Зачем: P&L по начислениям показывает, сколько заработано. Но продавцу так же важно, **когда и
сколько Ozon выплатит**, хватит ли денег на закупки, зарплату и налоги и не будет ли кассового
разрыва.

## 0. Две отдельные области (решение владельца, 14.10.2026)

| | **Финансы Ozon** | **Планирование** |
|---|---|---|
| Для кого | для всех | для тех, кому нужен прогноз денег; включается пользователем |
| Что внутри | только данные Ozon: P&L по начислениям (3.1–3.5), выплаты и баланс у Ozon с прогнозом следующих выплат (3.6), главная — дашборд Ozon (3.7) | выплаты Ozon по графику как главная строка поступлений плюс свои расходы и доходы, разовые и регулярные; платёжный календарь, прогноз остатка, кассовые разрывы, ДДС (3.8–3.10); банки — необязательный источник факта (3.11–3.12) |
| Нужен банк? | нет | нет: остаток и операции можно вести вручную; банк — удобство, а не условие |

**Дашборды не смешиваются.** На главной (дашборд Ozon) нет внешних операций и прогноза
остатка. У планирования свой обзор. Связь между областями одна: прогноз выплат Ozon из 3.6
попадает в планирование как плановые поступления; вручную их не вводят.

**Сервис универсальный (правило 13).** График выплат, условия оплаты поставщикам, своё
производство или перепродажа, статьи, налоги, банки — настройки пользователя с разумными
шаблонами. Никаких условий конкретного магазина в коде.

## 1. Выплаты Ozon — что известно (исследование, октябрь 2026)

Сайты Ozon (seller.ozon.ru, docs.ozon.ru) из облачной среды не открываются; сведения собраны
поиском по открытым статьям, и они **расходятся** — поэтому график в коде не зашиваем.

- **Стандартный график:** раз в неделю по средам, с переносом примерно на три недели;
  расчётный период — календарная неделя (пн–вс); выплата, выпавшая на выходной или праздник, —
  в следующий рабочий день. Так с конца 2024 года (до ноября 2024 — два раза в месяц). Часть
  статей 2026 года всё ещё описывает старую схему «аванс до 25-го, окончательный расчёт до
  15-го следующего месяца».
- **Гибкий график:** выплаты каждый рабочий день или раз в неделю — за процент от выплаты.
  Процент у источников разный (2,5 % / 1,5 %; без счёта в Ozon Банке — 4,49 % / 3,49 %); со
  счётом в Ozon Банке дешевле. Точный процент виден только в кабинете продавца.
- **Досрочная выплата** — по запросу, с комиссией. **Отсрочка выплат** — наоборот, снижает
  комиссию за продажу (например, на 14 дней — на 0,45 п.п.).
- **Вывод:** у каждого продавца свой график и своя комиссия, и они меняются. Сервис
  **определяет график по фактическим выплатам** из API, а пользователь может его поправить.

### Что даёт Ozon API (сверено с `docs/ozon/seller_api_2026-10.txt`)

| Метод | Что даёт | Как используем |
|---|---|---|
| `POST /v1/finance/balance` (бета, «Финансы → Баланс») | за период ≤ 30 дней: баланс на начало и конец, начислено, `payments[]` — суммы выплат, разбивка продаж, возвратов и услуг | **запрос на один день** (date_from = date_to): выплаты за этот день = выплата этого дня → история выплат с датами и баланс у Ozon по дням. Дат выплат в ответе нет — это предположение, проверить на реальном ключе (шаг 3.6) |
| `POST /v1/finance/cash-flow-statement/list` | итоги полумесяцев (1–15, 16–конец): баланс на начало и конец, выплаты за период | сверка: сумма дневных выплат = выплатам полумесяца |
| `POST /v1/finance/accrual/by-day`, отчёты XLSX | начисления по дням (шаги 1.4, 2.2) | какая неделя продаж за выплатой стоит, прогноз сумм |
| — | метода «график выплат» или «настройки выплат» **нет** | график определяется по истории + настройка пользователя |

## 2. Выплаты и баланс у Ozon (шаг 3.6, область «Финансы Ozon»)

- **История:** баланс у Ozon по дням → снимки `ozon_balance_days` (правило 12) → выплаты с
  датами (дни, где выплаты ≠ 0). При подключении ключа — история за 90 дней, дальше как
  начисления (вчера, сегодня, пропуски).
- **График определяется сам** по выплатам за последние 8–12 недель: дни выплат (каждый рабочий
  день → ежедневный; один день недели → еженедельный — какой), лаг (за какую неделю продаж
  выплата: сумма выплаты ≈ сумма начислений недели N недель назад) и комиссия гибкого графика
  (разница между ними). Пользователь видит «Определили: раз в неделю по средам, за неделю продаж
  3 недели назад» и может поправить. Нет истории (новый ключ) — стандартный график из справочника
  `app/data/ozon_payouts.json` (данные с датой действия, не константы).
- **Прогноз** на 4–8 недель: даты — по графику (праздник → следующий рабочий день, календарь —
  данные); сумма — начисления соответствующей недели продаж (они известны до выплаты) минус
  комиссия графика; ещё не закончившиеся недели — по среднему за 4 недели, с пометкой «оценка».
  Прогноз не обещает больше, чем лежит на балансе Ozon плюс будущие начисления.
- **Факт против прогноза:** выплата пришла — прогноз закрыт, расхождение видно; не пришла в
  ожидаемый день — сигнал (аномалия, шаг 7.1).
- **Страница «Выплаты Ozon»** (Финансы ▾): следующая выплата (дата, сумма, «по графику» или
  «оценка»), на балансе у Ozon сейчас, график по неделям (факт — сплошные столбики, прогноз —
  штриховка), таблица выплат, настройки графика.

## 3. Планирование (шаги 3.8–3.10)

### Принципы удобства (ПланФакт, КУБ24, Свóдно, западные сервисы прогноза денег)

- **Работает без банка.** «Сколько денег сейчас» — вручную, операции — вручную или списком по
  шаблону (правило 14). Банк по API или выписка — потом, как удобство.
- **Быстрый старт:** три вопроса → готовые статьи и предложенные регулярные платежи; всё правится.
- **Регулярные платежи** — начало, необязательный конец, периодичность (неделя / месяц / квартал /
  год), день. Отдельный платёж можно перенести, изменить сумму или пропустить. Любой план можно
  выключить и сразу увидеть, как меняется прогноз («что если»).
- **Горизонт** 4–8 недель по умолчанию (переключатель 30 / 60 / 90 дней); порог остатка
  пользователя; участки ниже порога и ниже нуля на графике — красным; «денег хватит до …».
- **План-факт:** плановый платёж закрывается отметкой «оплачено» (создаёт операцию) или
  операцией из банка; расхождение видно.
- **P&L и ДДС — разные отчёты.** P&L — по начислениям (раздел «Финансы Ozon»), ДДС — по деньгам
  (планирование). Не смешивать, подписывать.

### Профиль бизнеса — первый вход в планирование

**Каждый вопрос объясняет, зачем он и что изменит** (решение владельца) — иначе это выглядит как сбор
данных «для себя». Любой вопрос можно пропустить: тогда ничего не предлагаем и считаем как есть.

1. **Откуда товар** («чтобы правильно назвать себестоимость в P&L и предложить нужные платежи») — та же настройка, что подпись себестоимости в P&L (шаг 3.3,
   `user_settings.supplier_payment`), с новыми значениями:

   | Ответ | В P&L | В планировании |
   |---|---|---|
   | Закупаю, плачу при закупке | «Себестоимость с НДС» | закупки — плановые платежи по датам (вручную; позже — из планирования поставок 5.2) |
   | Поставщик получает деньги после продажи | «Долг поставщику» | генератор «оплата поставщику»: себестоимость проданного × НДС, раз в неделю / месяц |
   | Закупка с отсрочкой N дней | «Себестоимость с НДС» | оплата через N дней после закупки |
   | Своё производство | «Себестоимость производства» | регулярные расходы производства (сырьё и материалы, зарплата, аренда цеха) — обычные плановые платежи, не привязаны к продажам |
   | По-разному | «Себестоимость с НДС» | всё перечисленное доступно, генераторы включаются по отдельности |

2. **Куда приходят выплаты Ozon** — счёт или кошелёк («чтобы выплаты по графику сами появлялись в
   прогнозе — вводить их не нужно»).
3. **Сколько денег сейчас** — остаток на сегодня по каждому счёту: расчётный счёт, карта, наличные
   («от этой суммы строится прогноз: хватит ли денег до следующей выплаты Ozon»).

По ответам — шаблон статей ДДС (общие + перепродажа или производство) и предложения регулярных
платежей: реклама вне Ozon, зарплата, аренда, подписки, кредиты, налоги по налоговому профилю. Всё
предложенное — списком с галочками и строкой «зачем»: например, у расходов производства — «чтобы
прогноз остатка учитывал сырьё и зарплату; можно не добавлять».

### Откуда берётся план

- **выплаты Ozon** — прогноз из 3.6 (не вводятся вручную);
- **свои регулярные и разовые** доходы и расходы — вручную или шаблоном;
- **оплата поставщику** — генератор, только если выбран в профиле;
- **налоги, НДС и взносы** — по налоговому профилю (шаг 2.5) и срокам из `docs/TAXES.md`; при
  смене режима прошлые платежи пересчитываются только с согласия пользователя (решение владельца);
- позже — **закупки из планирования поставок** (5.2).

Прогноз остатка = остаток сейчас + плановые поступления − плановые платежи; день, где прогноз
ниже нуля (или порога), — кассовый разрыв.

## 4. Модель данных (набросок)

**Финансы Ozon (3.6):**
- `ozon_balance_days` — баланс у Ozon за день: на начало, начислено, выплачено, на конец,
  разбивка, сырой ответ, время загрузки. Снимок; повтор дня без изменений новой записи не создаёт.
- `ozon_payout_settings` — график выплат с историей (`effective_from`): auto | standard |
  flexible_daily | flexible_weekly (+ день недели) | custom; лаг в неделях, комиссия графика %.
- выплаты Ozon — производные из `ozon_balance_days` (дни с выплатами), их можно пересчитать.

**Планирование (3.8–3.10):**
- `money_accounts` — счета и кошельки: название, тип (расчётный счёт, карта, наличные, кошелёк),
  источник (manual | bank), архив; начальный остаток — `money_account_balances` (на начало дня,
  исправление — новая запись). ✅ 3.8
- `money_operations` — факт: дата, сумма (+ приход / − расход), счёт, статья, контрагент,
  комментарий, источник (manual | import | ozon_payout | bank), перевод между своими счетами
  (две операции с общим `transfer_id`). Правило 12: версии по `op_id`, удаление — скрытие. ✅ 3.8
- `cash_categories` — статьи пользователя (шаблон по профилю бизнеса — `app/data/cash_categories.json`). ✅ 3.8
- `planned_payments` — разовые и регулярные: правило повторения (неделя / месяц / квартал / год, день, начало,
  конец), сумма, статья, счёт, контрагент, включён ли; закупка с отсрочкой — `purchase_day` (оплата = закупка + N дней
  из настроек). Изменения плана — новая версия (DATA_HISTORY). ✅ 3.9
- `planned_overrides` — отдельный платёж по ключу (`plan:<id>:<дата>`, `ozon:<дата>`, `supplier:<начало периода>`,
  `tax:<график>:<что>:<начало периода>:<срок>`): перенос, своя сумма, пропуск, «оплачено» (операция или дата и сумма
  отметки). Платежи генераторов не хранятся — пересчитываются. ✅ 3.9
- `planning_settings` — + генераторы `gen_ozon`, `gen_supplier`, `gen_taxes`, день оплаты поставщику
  (`supplier_period` неделя | месяц, `supplier_day`). ✅ 3.9
- настройки планирования `planning_settings`: включено ли, мастер пройден, куда приходят выплаты Ozon, порог
  остатка, горизонт. ✅ 3.8

**Банки (3.11 ✅, 3.12 ✅, 8.5):** `bank_statements` (файл выписки), `bank_transactions` (операция банка: `dedup_key`,
ИНН и счёт контрагента, назначение, вид regular | ozon | transfer, `op_id`), `bank_balances`, реквизиты счёта в
`money_accounts` (номер, БИК, банк) → те же `money_operations` с источником `bank`; 3.12 ✅ — `bank_connections` (токен —
шифротекст, статус, до какого дня загружено), `categorization_rules` (условия → статья, порядок), у операции — кто поставил
статью (`category_by`: вручную / правило / встроенное). Поступление от Ozon в банке (ИНН плательщика из
справочника; Ozon — ООО «Интернет Решения», ИНН 7704217370) — факт выплаты Ozon, а не вторая
операция: одна операция, сверка суммы и даты.

## 5. Дашборды

**Главная — дашборд Ozon (шаг 3.7), только данные Ozon:**
- цифры: продано, начислено к получению, прибыль и маржа (P&L, бейдж источника), на балансе у
  Ozon, следующая выплата (дата и сумма);
- графики: выручка по дням / неделям с прошлым периодом; выплаты Ozon по неделям — факт и прогноз;
- виджеты следующих фаз (остатки — 5.1, изменения цен — 6.4, аномалии — 7.2) — в своих шагах.

**Обзор планирования (шаг 3.10 ✅), первая вкладка раздела «Планирование»:**
- цифры: деньги сейчас (по счетам), ближайшая выплата Ozon, ближайший кассовый разрыв или
  «денег хватит до …», ожидается за выбранный горизонт: поступления и платежи;
- график: линия прогноза остатка по дням с порогом; столбики — выплаты Ozon (свой цвет), прочие
  поступления, платежи; слева от «сегодня» — факт, справа — план;
- ближайшие платежи и поступления на 14 дней с отметкой «оплачено»; ДДС по статьям — вкладка.
- ДДС (`engine/cash_flow.py`): остаток на начало, поступления и платежи по статьям и неделям / месяцам, остаток на
  конец; переводы между своими счетами — не приход и не расход. Остаток на начало дня — от начального остатка
  счёта вперёд или назад по операциям; по счёту без остатка есть движение — остатки по периодам не считаем.

## 6. Банки по API (шаги 3.11, 3.12, 8.5) — необязательный источник факта

Общий интерфейс `BankProvider` (как `CostProvider` у парсеров): проверить доступ, список счетов,
операции за период, остатки. Новый банк — новая реализация. Токены банков — только
Fernet-шифротекст, не логируются и не возвращаются (правило 7). Только права на чтение выписок.

| Банк | Что известно | Когда |
|---|---|---|
| Любой | выписка файлом в формате обмена с 1С (`1CClientBankExchange`, обычно windows-1251) — её выгружает любой интернет-банк | шаг 3.11 ✅ |
| Т-Банк | T-API: `GET business.tbank.ru/openapi/api/v1/statement` (прежний `bank-statement` помечен устаревшим) — порции до 5000 с `cursor`, 20 запросов/с, данные с июня 2023; Bearer-токен выпускает сам клиент в Т-Бизнесе; выжимка — `docs/banks/TBANK.md`, сверено с официальной OpenAPI и песочницей | шаг 3.12 ✅ |
| Точка | спецификация — `docs/banks/TOCHKA.md` (выжимка) и `docs/banks/tochka/`: выписка асинхронно, остатки, вебхуки; клиент вставляет токен своей интеграции; песочница есть | шаг 3.12 ✅ |
| Модульбанк | по открытым источникам не подтверждено, документация из облачной среды не открывается — не сделан; до тех пор — выписка файлом | позже, если API доступен клиенту |
| Сбер | СберБизнес API: токены из кабинета, сертификат электронной подписи, для платформ — партнёрская авторизация СберБизнес ID | шаг 8.5 |
| Альфа, ВТБ и др. | открытого API выписки для малого бизнеса не нашли; вероятно, только партнёрские программы | шаг 8.5; до тех пор — выписка файлом |

Подключение — меню аккаунта → «Банки» (3.12 ✅): токен проверяется в банке до сохранения; обновление раз в час и кнопкой;
при подключении — история, насколько отдаёт банк; та же операция из файла и из API — не дубль. Правила разнесения — в
«Статьях»: условия (ИНН, контрагент, слова в назначении, направление, сумма) → статья, по порядку; встроенные —
маркетплейс по ИНН, перевод между своими счетами, налог по реквизитам казначейства (ЕНП закрывает плановый налог с
ближайшим сроком). Ручная разметка важнее правил; из неё — предложение «правило для контрагента».

Отправку платежей из сервиса не делаем — только чтение. Если понадобится — отдельный шаг с
правилами безопасности как для цен (dry-run → подтверждение → аудит).

| ПланФакт | ДДС, ОПиУ, баланс; данные Ozon и WB (выручка, комиссии) попадают в отчёты сами; платёжный календарь показывает дефицит денег до его появления |
| Свóдно | управленческая прибыль = выплата маркетплейса − себестоимость − расходы, не привязанные к заказу; календарь — с учётом сроков выплат площадки и плана закупок |
| Сервисы прогноза денег (Float, Cash Flow Frog, FlowCast и др.) | регулярные операции с началом, концом и правкой отдельного платежа, сценарии «что если», порог остатка с подсветкой на графике, «денег хватит до …», сверка прогноза с фактом |

**Наше отличие:** мы уже знаем, что начислено и что лежит на балансе у Ozon, видим фактические
выплаты и сами определяем график — прогноз главного поступления продавца без ручного ввода и
без обязательного банка.

**Не делаем (пока):** отправку платежей, счета и акты, бухгалтерию; бюджеты и права сотрудников —
после запуска, по запросу пользователей.
