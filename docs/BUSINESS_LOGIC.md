# Бизнес-логика

Всё, что здесь описано, уже отработано на реальных данных магазина в рабочем
HTML-калькуляторе (`reference/ozon_calculator.html`). При переносе в бэкенд
логику не менять — только переписывать на Python и покрывать тестами.

Числа и условия здесь — магазина владельца: это эталоны для тестов и пример, а не умолчания
для всех (правило 13). Себестоимость, налог и НДС, пороги и параметры у каждого пользователя
свои — что и в каком шаге становится настройкой, см. `docs/ROADMAP.md`, «Универсальность».

## 1. Два типа отчётов Ozon

Пользователь выгружает из личного кабинета Ozon XLSX-файлы двух типов.

### 1.1 «Отчёт по начислениям» (обычно недельный)

Финансы → Отчёт по начислениям. Один лист, одна плоская таблица.

- Строка 1: `Период: 07.09.2026-13.09.2026`
- Строка 2: заголовки. Важные колонки (искать по названию, не по позиции):
  `Тип начисления`, `Артикул`, `SKU`, `Название товара`, `Количество`, `Сумма итого, руб.`
- Дальше — строки начислений. Каждая строка — одна операция одного типа
  («Выручка», «Вознаграждение за продажу», «Логистика», «Баллы за скидки» и т.д.).

Признаки для определения типа: в одной строке есть «тип начислен…» и «сумма итого».

Строки без «Тип начисления» — не операции Ozon (у каждой операции тип есть). В выгрузках
владельца под таблицей бывают ручные пометки в колонке «Сумма итого» («Придет на счет»,
«Итого» — см. `fixtures/accrual_2026-08-01_09.xlsx`). В `auto_total` они не входят;
пользователь получает предупреждение с их количеством и суммой.

**Подвох с кодировкой:** Ozon иногда записывает кириллицу в XML как сущности
`&#x422;&#x438;&#x43F;`. openpyxl это декодирует сам; в браузерной версии
пришлось отдельно распаковывать ZIP и заменять сущности. В Python проблемы нет,
но тест на реальном файле обязателен.

### 1.2 «Отчёт о реализации» (месячный)

Финансы → Отчёт о реализации. Один лист, перед таблицей ~12 строк шапки
(реквизиты, период «Реализация товаров за период с … по …»).

- Главный заголовок таблицы: строка, где есть `Артикул` и (`Название товара` или `№ п/п`).
- Следующая строка — подзаголовок: `Реализовано на сумму, руб.`, `Кол-во` и т.п.
  **Колонки надо искать в обеих строках.**
- Ещё ниже — строка с номерами столбцов (1, 2, 3 …), её пропускать.
- Строки данных: в первой колонке — порядковый номер (целое > 0).
- Период — из строки «Реализация товаров за период с … по …» (строкой выше есть
  «Отчет о реализации № … от 31.08.2026» — эту дату за период не принимать).
- После таблицы — итоговые строки; значение лежит в соседней ячейке справа от подписи:
  - `Итого реализовано (за вычетом возвратов) (руб.):`
  - `Всего выплат от партнёров (руб.):`

Признаки для определения типа: в строке есть «артикул» и «реализовано»,
и **нет** «тип начисления» (это был бы отчёт по начислениям) и **нет** «показной»
(у Ozon есть похожий «Показной отчёт о реализации» — его не путать).
Имя файла можно использовать только как дополнительный сигнал.

## 2. Справочник себестоимости

Свой у каждого пользователя: он вносит себестоимость сам — в таблице или по шаблону
(шаги 2.3–2.4), цена закупки **без НДС** за единицу, с историей. `reference/cost_prices.csv` —
78 артикулов владельца, только для тестов и эталонов.
Артикул в отчётах Ozon совпадает с ключом справочника посимвольно
(например `6001-2RS.C3.SRL.NAC.TH`).

Если артикула нет в справочнике — **не подставлять 0**, а вернуть его в списке
`missing_cost` (артикул, SKU, название, количество) и показать предупреждение:
прибыль в таком случае завышена.

## 3. Расчёт P&L (одинаковый для обоих отчётов)

Параметры владельца (на них эталоны ниже): `vat_multiplier = 1.22`, налог 20 % от прибыли.
У каждого пользователя налог и НДС считаются по его налоговому профилю (ИП / ООО, система
налогообложения, НДС — шаг 2.5, `docs/TAXES.md`); формула ниже — режим «Свой процент от прибыли».

```
auto_total      — сколько придёт от Ozon:
                  • начисления: сумма колонки «Сумма итого» по ВСЕМ строкам
                  • реализация: «Итого реализовано» + «Всего выплат от партнёров»
effective_total = manual_total, если пользователь ввёл своё значение, иначе auto_total

cost_sales      = Σ (себестоимость_единицы × количество)
                  • начисления: только по строкам с типом «Выручка»
                  • реализация: по всем строкам товаров
owed            = cost_sales × vat_multiplier        — долг поставщику с НДС
profit_before_tax = effective_total − owed
tax             = max(0, profit_before_tax × tax_rate)
net             = effective_total − owed − tax        — остаток владельцу

revenue_base    — база для процентов и маржи:
                  • начисления: сумма строк «Выручка»
                  • реализация: «Итого реализовано»
margin          = net / revenue_base × 100; если revenue_base = 0 → None («—» в UI)
```

Ручная сумма (`manual_total`) — это поправка, когда фактическая выплата на счёт
отличается от расчётной. Модель: `auto_total` / `manual_total` / `effective_total`.
Очистка ручного значения возвращает к авто. Все зависимые показатели
пересчитываются от `effective_total`.

### Проценты в таблице «Начисления по типам»

Доходы и расходы считаются **каждая группа в 100% отдельно**
(иначе «Выручка 100% + Баллы 86% + …» даёт больше 100%, что сбивает с толку):

- доход: `сумма_типа / Σ положительных × 100`
- расход: `|сумма_типа| / Σ |отрицательных| × 100`
- блок P&L (долг, прибыль, налог, остаток): `% от revenue_base`
- прибыль выделяется отдельным цветом (синим), остаток — зелёным/красным.

## 4. Минимальная и целевая цена

Часть расходов — процент от цены, часть — фиксированные суммы:

```
P = (C × VAT + L + S + X) / (1 − comm − adv − acq − M)

C    — себестоимость без НДС          VAT  — НДС поставщика по профилю (у владельца 1.22)
L    — логистика, ₽ (фикс)            S    — хранение, ₽ (фикс)
X    — прочие фиксированные, ₽
comm — комиссия Ozon, доля            adv  — реклама, доля
acq  — эквайринг, доля                M    — желаемая маржа, доля

min_price    — при M = 0
target_price — при M = целевая маржа
```

Если знаменатель ≤ 0 — цена недостижима, вернуть ошибку, а не бесконечность.

Параметры магазина владельца (пример, не умолчания): комиссия FBO ~38% от цены,
реклама ~6%, возвраты ~4%, «звёздные товары» ~0.2%, логистика — фиксированная
сумма на SKU, налог 20% от прибыли. В сервисе: комиссия и логистика — из данных Ozon
по товару, реклама, возвраты и целевая маржа — настройки пользователя, налог и НДС с
продажи — налоговый профиль (шаг 2.5); налог с выручки входит в знаменатель как доля.

Как сделано в сервисе (шаг 4.2, `engine/price_calculator.py`): прибыль с 1 шт. до налога на прибыль линейна —
`π(P) = α × P − β`, минимальная цена `β / α`, целевая `β / (α − M)`, округление вверх до копейки.

- НДС с продаж входит в цену: доля `v / (100 + v)`. Без вычетов он целиком расход; с вычетом («общий» НДС) к уплате —
  минус НДС поставщика и НДС в услугах Ozon, поэтому всё считается без НДС (при тех же условиях минимальная цена та же).
- Налог с дохода (УСН «Доходы», АУСН «Доходы», НПД, свой процент от выручки) — доля дохода без НДС, в знаменателе.
- Налог с прибыли на минимальную цену не влияет (прибыль 0); целевая маржа M — до него, как маржа в «Прибыли по
  товарам». Патент, взносы и минимальный налог — годовые, на штуку не делятся.
- Логистика L — фактическая по товару: логистика из начислений / проданные штуки (с обратной логистикой) за 30 дней,
  товар не продавался — за 90, и тогда — средняя по магазину; данных нет совсем — расчёта нет. Ozon в ценах
  (`/v5/product/info/prices`) отдаёт только последнюю милю и обратный поток, без логистики FBO.
- «Возвраты ~4 %» отдельной долей не вводятся: обратная логистика уже в L. Хранение S и прочее X — по желанию,
  только для расчёта (Ozon не делит хранение по товарам).
- Умолчания: реклама 0 %, целевая маржа 20 % — меняются в настройках.

## 5. Планирование поставок (без ML)

```
avg_daily    = продажи за 30 дней / 30
trend        = (продажи за 7 дней / 7) / avg_daily
days_left    = остаток / (avg_daily × trend)
target_stock = avg_daily × target_days        (по умолчанию 45, настройка пользователя)
to_order     = max(0, target_stock − остаток)
срочность:   < 7 дней — critical, < 14 — urgent, < 30 — planned
```

Считать отдельно по каждой паре SKU × склад.

Как сделано в сервисе (шаг 5.2, `engine/supply_planner.py`, решения владельца 16.10.2026):

- Продажи — заказы без отмен из отправлений Ozon (`/v3/posting/fbo/list`, `/v4/posting/fbs/list`), а не начисления: в
  начислениях склада нет. Для складов Ozon (FBO) пара — **SKU × кластер покупателя** (`cluster_to`): Ozon принимает поставку
  в кластер и сам раскладывает по складам; по складу отгрузки продажи «переезжают» туда, где товар есть. Для своих складов
  (FBS / rFBS) — SKU × склад продавца, и это **закупка на свой склад**, а не поставка в Ozon.
- Окно — 30 полных дней до сегодня (последние 7 из них — тренд), но не раньше, чем загружены отправления, и не позже
  последней синхронизации; дней с данными меньше 7 — не считаем. `avg_daily` = продажи / дней с данными.
- Остаток: кластер — доступно на складах Ozon этого кластера, свой склад — доступно минус резерв (зарезервированное уже
  продано). `days_left` = остаток / (avg_daily × trend) — без того, что в пути; за 7 дней продаж нет — `None`.
- `to_order` = max(0, ⌈avg_daily × (target_days + lead_time_days)⌉ − остаток − в пути): пока поставка едет
  (`lead_time_days`, по умолчанию 7), товар продаётся — довозим и это. `target_stock` = ⌈avg_daily × target_days⌉ —
  для справки. `target_days` (45) и `lead_time_days` (7) — настройки пользователя.
- Срочность — по порогам остатков пользователя (5.1): days_left < «Критично» (7) — «Срочно», < «Мало» (14) — «Скоро»,
  остальные с `to_order` > 0 — «Плановые» (вместо «< 30»: цель 45 дней больше 30, иначе часть рекомендаций потерялась бы).
  Кончится раньше, чем доедет поставка (days_left < lead_time_days), — отдельное предупреждение.
- Только пары с продажами за 30 дней. Покупают в кластере, где товара нет совсем, — рекомендация «везти с нуля».

## 6. Вывоз неликвида со складов (уже делали вручную)

Логика, которую владелец применял к выгрузке «Управление остатками»:
сортировать товары по «дней без продаж» (хуже — первыми), вывозить почти весь
остаток, оставляя 2 шт в каждом кластере; у нормально продающихся — оставлять 10+.
Кластер «Санкт-Петербург и СЗО» не трогать. Пригодится в фазе 5.

Числа (2 шт, 10+) и исключённый кластер — решения владельца: в сервисе это параметры отчёта,
которые пользователь сохраняет; по умолчанию ни один кластер не исключён.

Как сделано в сервисе (шаг 5.1, `engine/withdrawal.py`, отчёт «Кандидаты на вывоз»):

- Кандидат — товар со статусом «Избыток» (запаса больше порога «Избыток», по умолчанию 60 дней, или не продаётся при
  остатке) и остатком на складах Ozon (FBO). Со своих складов (FBS / rFBS) вывозить нечего, но их остаток входит в
  запас товара. Продажи неизвестны — не кандидат.
- Не продаётся (продаж за 30 дней нет) — в каждом кластере оставляем `keep_idle` шт. (2), остальное на вывоз.
- Продаётся — в кластере оставляем `keep_selling` шт. (10) и всего вывозим не больше излишка: остатка сверх запаса на
  порог «Избыток» (`остаток − ⌈продажи в день × порог⌉`) — после вывоза товара хватает ровно до порога, он не кончится.
- «Дней без продаж» — от последнего дня с продажей в `sales_daily` до сегодня, по товару в целом (склада в начислениях
  нет); продаж в данных нет — хуже любого числа. Порядок: дольше не продававшиеся → больше дней запаса → больше остаток.
- Внутри товара — сначала кластеры с большим остатком, в кластере — склады с большим остатком. Лимит «вывезти всего»
  идёт по общему порядку, последняя строка — частично. Исключённые кластеры не трогаем.
- Параметры по умолчанию: без лимита, 2 и 10 шт., ни один кластер не исключён. Ozon-овские `days_without_sales_cluster`
  и `ads_cluster` из `/v1/analytics/stocks` не используем — дни запаса и продажи считаем по своим данным (решение 1.3).

## 7. Аномалии — пороги по умолчанию

Проверки данных (синхронизация, пропуски начислений, отчёты, себестоимость) и избыток запаса, деньги под риском и порядок
«Требует внимания» — §10, «Требует внимания» (шаг 10.5).

Пользователь меняет их в настройках (шаг 7.1).

| Метрика | Жёлтый | Красный |
|---|---|---|
| Продажи (3 дня vs предыдущие 7) | падение > 40% | падение > 70% |
| Продажи — рост | > 200% (проверить цену) | — |
| Цена | изменение > 10% | > 30% |
| Комиссия | изменение > 2 п.п. | — |
| Маржа | — | ниже порога пользователя (10%) |
| Дней запаса | < 14 | < 7 |
| Автодобавление в акцию | сразу | — |
| Маржа в акции | — | < 0% |

Не создавать дубль, если активная аномалия того же типа уже есть.

### Как сделано в сервисе (шаг 7.1, `engine/anomaly_detector.py`, `services/anomalies.py`)

Пороги — «Основные настройки → Аномалии и порог маржи» (умолчания — таблица выше); дни запаса — пороги остатков 5.1
(меньше «Мало» — жёлтая, меньше «Критично» — красная). Порог «низкой маржи» — одна настройка на весь сервис: акции,
товары, цены, прибыль по товарам и аномалия. Проверка — раз в час (Celery, :57), по данным, уже загруженным в сервис.

- **Записи не удаляются.** Активная аномалия одного типа и одного предмета (магазин, товар, товар × акция, день
  выплаты) — одна (частичный уникальный индекс). Прошла — `resolved_at` и причина: `normal` — вернулось в норму,
  `escalated` — жёлтая стала красной (новая запись, жёлтая остаётся в истории), `gone` — проверка больше не относится
  (товар в архиве, «Планирование» выключено). Красная, ставшая слабее, остаётся красной до нормы. Повторное появление —
  новая запись. «Ок» (`is_acknowledged`) — видел: аномалия активна, пока метрика не вернётся, но в счётчик не входит.
- **Нет данных ≠ норма и ≠ 0.** Нечем судить (дни без данных, продажи неизвестны, маржу не посчитать, остатки на счетах
  не указаны, выписки за эти дни ещё нет) — новых не создаём, активные не закрываем. Сбой одной проверки — её аномалии
  остаются как были.
- **Продажи** (магазин и каждый товар в продаже — решение владельца 17.10.2026): последние 3 полных дня (до вчера) против 7
  дней перед ними, только дни с данными (из трёх — хотя бы 2, из семи — 5). Ожидание с поправкой на выходные: доля
  рабочих и нерабочих дней (выходные и праздники — `engine/workdays`) по продажам магазина за 4 недели; ожидали =
  продажи 7 дней / сумма долей их дней × сумма долей последних дней. Падение больше порога (40 / 70 %) или рост больше
  200 % — только если это не случайность: у малых продаж (Пуассон) вероятность такого числа меньше 1 % (у товара с 1
  продажей в день три дня без продаж — не аномалия, с 5 в день — да). Закрывается, когда изменение меньше половины
  порога, — без «мигания» вокруг порога. Товар с нулевым остатком не судим — его покажут «дни запаса».
- **Цена и комиссия:** сейчас против 7 дней назад (последний снимок не позже начала окна; снимков тогда ещё не было — первый
  снимок). Цена — больше 10 % жёлтая, больше 30 % красная; комиссия — больше 2 п. п. жёлтая. Изменения через сервис (6.2–6.4)
  — тоже аномалия, с пометкой «через сервис» (решение владельца 17.10.2026). Цена вернулась — закрывается; через 7 дней
  новая цена становится обычной — закрывается. Цена 0 («не задана») — не судим.
- **Маржа ниже порога** (красная) — калькулятор 4.2 при текущей цене, у товара, который продаётся: не в архиве, есть
  остаток или были продажи за 30 дней (решение владельца 17.10.2026). **Маржа в акции < 0** — красная, у участия в
  незакончившейся акции. **Автодобавление** — жёлтая, пока товар в акции.
- **Выплаты Ozon** (без банка): не пришла по графику (просрочка шага 3.6 — день графика за 2 недели, окно 4 дня, только по
  загруженным дням) — красная, закрывается, когда после ожидаемого дня пришла любая выплата; выплата за 14 дней разошлась
  с прогнозом по графику больше чем на 10 % — жёлтая. График, найденный по выплатам с низкой уверенностью, на расхождение
  не сверяем — расходился бы каждую неделю.
- **Только при включённом «Планировании»:** выплата не дошла до счёта (сверка 3.11 `no_bank`: выписка за эти дни есть,
  поступления нет) — красная, пришло с разницей от 1 ₽ — жёлтая (нужна выписка или банк по API); кассовый разрыв в
  ближайшие 14 дней (прогноз 3.9: ниже нуля — красная, ниже порога остатка — жёлтая); операции без статьи дольше 7 дней
  (от появления операции в сервисе) — одна жёлтая на все.

## 8. Безопасность изменения цен

Обязательные ограничения (жёсткие, не отключаются пользователем):

- только через dry-run: сначала предпросмотр, потом применение по ID предпросмотра;
- изменение не больше 20% за раз;
- новая цена не ниже `себестоимость × 1.05`;
- пауза между изменениями одного товара — 1 час;
- > 10 товаров — дополнительное подтверждение, > 50 — ввод слова «ПОДТВЕРЖДАЮ»;
- максимум 500 товаров за запрос, в Ozon — батчами по 100 с паузой 2 сек;
- каждое действие — в `audit_log` с данными до/после, запросом и ответом Ozon;
- откат — только для изменений не старше 7 дней, откат отката запрещён;
- если данные из Ozon выглядят аномально (цена 0, комиссия 99%, отклонение
  от медианы за 30 дней > 50%) — ничего не применять автоматически.

Автоматические правила (фаза 9) — только после нескольких месяцев ручного режима
без инцидентов: ≤ 20 товаров за запуск, ≤ 50 изменений в день, > 10 за час — пауза
до ручного подтверждения, уведомление в Telegram о каждом действии.

### Как сделано в сервисе (шаг 6.1, `services/price_safety.py`)

Проверяющий `PriceSafetyChecker` говорит, можно ли отправить новую цену: errors блокируют, warnings нет. Лимиты —
константы модуля, у проверяющего нет других параметров, кроме режима (вручную | правило) и времени.

- Себестоимость — на сегодня, с НДС (ставка записи справочника или налогового профиля, как в калькуляторе 4.2), граница —
  `себестоимость с НДС × 1,05` с округлением до копейки (как вход в акции, 4.3). Нет себестоимости — нельзя (правило 5).
  Граница действует и для новой минимальной цены: ниже неё Ozon сам опускает цену в акциях.
- 20 % — от текущей цены Ozon (последний снимок); ответ подсказывает, какую цену можно поставить за один раз (±20 % и
  не ниже границы). Цены Ozon нет (0 = не задана) — не с чем сравнить, нельзя.
- Пауза — час от последнего изменения через сервис, которое дошло до Ozon (применено или Ozon не ответил); отклонённые
  и заблокированные не считаются. Относится к товару целиком: цена и минимальная цена.
- Данные Ozon аномальны: цены нет, комиссия от 90 % (порог 4.3) — нельзя. Медиана за 30 дней — по цене на конец каждого
  дня (дни, когда цена была известна; меньше 7 таких дней — не проверяем). Дальше 50 % от медианы текущая цена (сбой
  данных или резкое изменение в кабинете Ozon) или новая (цена «уехала» за несколько шагов по 20 %): **вручную —
  предупреждение, в автоправилах — блокировка** (решение владельца 16.10.2026: иначе после смены цены в кабинете Ozon
  сервисом нельзя было бы пользоваться до 15 дней).
- Минимальная цена — ниже цены и не меньше 50 % от неё (иначе Ozon не примет), в том числе когда меняется только цена.
- **Откат** (решение владельца 16.10.2026) — без паузы и лимита 20 % (иначе снижение на 20 % не откатить одним шагом: обратно
  это +25 %), но только: ровно к цене «до» и только то, что меняло изменение, изменению не больше 7 дней, оно дошло до Ozon, само не откат и ещё не
  откачено, и цена в Ozon с тех пор не менялась (сейчас — ровно та, что поставило изменение). Себестоимость × 1,05,
  минимальная цена и аномалии данных проверяются и для отката.
- Запрос целиком (`check_request`): ничего не выбрано или больше 500 — нельзя; товар дважды — нельзя; больше 10 —
  подтверждение, больше 50 — слово «ПОДТВЕРЖДАЮ» (регистр и пробелы по краям не важны).

Журнал (`audit_log`, шаг 6.1): кроме действий в Ozon, middleware пишет каждый изменяющий запрос к API (POST, PUT,
PATCH, DELETE) вошедшего пользователя — метод, путь, HTTP-статус, IP, User-Agent; без тела запроса (пароли, ключи).
Предпросмотры и расчёты эндпоинт помечает «не изменение» — их нет. Действие и его запрос связаны общим `request_id`.
Записи не меняются и не удаляются — в Postgres это запрещает триггер; удалить можно только намеренно
(`SET LOCAL app.audit_log_allow_delete = 'on'`, например при удалении аккаунта, когда оно появится).

Цена не ниже зачёркнутой (цены до скидки) — блокировка: Ozon её не примет (`old_price_less_than_price`), а зачёркнутую
сервис не меняет — её меняют в кабинете Ozon (решение владельца 17.10.2026). Диапазон «за один раз» — ниже зачёркнутой.

### Изменение цены одного товара (шаг 6.2, `services/price_updater.py`)

- Предпросмотр: текущая цена — свежая из Ozon (изменилась — новый снимок); Ozon сейчас недоступен — по последнему
  снимку с предупреждением. Проверки §8, было → станет, маржа и «останется с 1 шт.» калькулятором 4.2. Предпросмотр —
  запись `price_changes` (status preview), живёт 15 минут; в Ozon ничего не уходит.
- Применение — только по `preview_id`: свой, не старше 15 минут, ещё не применялся (один предпросмотр — одна попытка),
  без ошибок. Цена в Ozon проверяется снова (не получили — не применяем), не должна измениться после предпросмотра,
  проверки §8 — заново (пауза, себестоимость могли измениться). Отказ проверок — запись `blocked` и журнал.
- Попытка записывается до запроса в Ozon со статусом «не ответил — могло примениться»: если сервис упадёт посреди
  запроса, история это честно покажет, а часовая пауза её учтёт. Ответ Ozon: `updated` — применено (новый снимок с
  поставленной ценой), иначе отказ с причиной Ozon понятным текстом; ошибка запроса — «ничего не изменилось»; таймаут —
  «могла измениться, проверьте через 1–3 минуты».
- Меняется только цена: минимальная (для автоакций Ozon) и зачёркнутая — нет.

### Массовое изменение цен (шаг 6.3, `services/price_bulk.py`)

- Откуда новые цены: стратегия для выбранных товаров — целевая маржа M % (цена калькулятором 4.2), +X % к текущей цене
  (можно с минусом), минимальная цена (без убытка) + X %; или файл — шаблон с текущими ценами, где меняют колонку
  «Новая цена» (правило 14). Цена не меняется — товара нет в предпросмотре («без изменений»); файл без правок — 0 изменений.
- «Не больше 20 % за раз» (по умолчанию включено): если цена по стратегии дальше допустимого за один раз, ставится
  ближайшая допустимая (±20 %, не ниже себестоимости с НДС + 5 %, ниже зачёркнутой), остальное — следующим шагом не
  раньше чем через час; у товара пояснение «по стратегии — …, за один раз можно до …». Выключено — такие товары
  блокируются.
- Предпросмотр — не больше 500 товаров, свежие цены из Ozon одним запросом, проверки §8 по каждому: «применится»,
  «с предупреждением», «заблокировано». Живёт 15 минут.
- Применение: считаются товары, которые применятся (с предупреждениями — только если их явно включили). Больше 10 —
  галочка подтверждения, больше 50 — слово «ПОДТВЕРЖДАЮ» (регистр не важен). Цены снова свежие из Ozon (не получили —
  ничего не меняем), изменилась после предпросмотра или проверки не прошли — этот товар не меняется, остальные — да.
  В Ozon — по 100 товаров с паузой 2 с; ошибка одного запроса не останавливает следующие. Товары в очереди уже
  учитываются часовой паузой.

### История и откат (шаг 6.4, `services/price_history.py`, `price_updater.rollback_preview`)

- История — все попытки изменить цену через сервис (вручную, списком, откаты), применённые и нет; предпросмотры не входят.
- Откат — тот же путь, что изменение одного товара: предпросмотр отката (в Ozon ничего не меняется, цена — свежая из Ozon) →
  «Вернуть …» по preview_id → журнал (действие «Откат цены»). Правила отката — выше (решение владельца 16.10.2026); откатить
  можно и одно изменение из массового. Причина — «Откат изменения от ДД.ММ.ГГГГ ЧЧ:ММ МСК».
- В списке «Откатить» — по последней известной сервису цене (быстрая проверка); полная проверка со свежей ценой из Ozon —
  в предпросмотре отката.

### Вход и выход из акций (шаг 4.3)

Тот же порядок: предпросмотр (ничего не меняется, в Ozon не ходим) → `confirm=true` (те же проверки заново) → запрос
в Ozon → `audit_log`. Жёсткие проверки: акция не закончилась и не заморожена; товар — кандидат или участник; цена в
акции > 0, ниже обычной и не выше максимальной для участия; не ниже себестоимости с НДС × 1,05 (нет себестоимости —
нельзя); данные Ozon не аномальны (есть цена, комиссия < 90 %); одна пара товар × акция — не чаще раза в час (выход не
ограничен); маржа в минус — только с явным «понимаю». Скидка больше 70 % — предупреждение.

## 9. Изменения Ozon, которые нужно учитывать

- **8 сентября 2026** (по документации Ozon; объявляли 6 июля) отключён `/v3/finance/transaction/list`. Использовать
  `/v1/finance/accrual/*`. Данные API могут расходиться с личным кабинетом

  без указания — по лимиту; выше лимита указать нельзя. Новое значение начинает
  действовать через день (указано до 23:59 МСК → действует послезавтра).

## 10. Карта сервиса: аналитика, рекомендации, запасы, бюджеты (фаза 10, `docs/SITEMAP.md`)

Определения для шагов 10.x — одинаковые во всех разделах (главная, аналитика, товары, финансы). Числа по умолчанию — не
данные владельца, а умолчания, которые пользователь меняет в настройках (правило 13). Точные формулы и эталоны для
тестов дописывает шаг, который их реализует.

### Показатели
- **Выручка, прибыль, маржинальность** — как в P&L (§3, шаги 3.1–3.4): выручка — продано по цене Ozon после его скидки
  («Выручка» в начислениях), прибыль — остаток после налога (если налог есть в обоих сравниваемых периодах, иначе до
  налога — как на главной 3.7), маржинальность = прибыль / выручка.
- **Заказы** — отправления (шаг 5.2) по дате создания, кроме отменённых; штуки заказов — сумма позиций. **Продажи** —
  проданные штуки по начислениям («Выручка», `sales_daily`, шаг 3.5). **Возвраты** — штуки и сумма «Возврата выручки».
  Заказ и продажа — разные события (продажа — когда Ozon начислил выручку), на графиках подписываются раздельно.
- **Средняя цена** = выручка / проданные штуки; штук нет — «—».
- **Прошлый сопоставимый период** — как на главной 3.7 (`dashboard.previous_period`): целые месяцы — столько же месяцев
  раньше; с 1-го по N-е — прошлый месяц с 1-го по то же число; иначе — столько же дней перед периодом.
- **Детализация** — день / неделя (пн–вс) / месяц; неполная неделя или месяц на краях периода помечается. Дни без данных
  — пропуск, а не 0 (правило 12).
- **Категория товара** — категория Ozon (`category_id` товара, названия — из справочника категорий Ozon, шаг 10.3).

**Как сделано (шаг 10.3, `engine/metrics.py`, `services/analytics.py`, эталоны — `tests/test_analytics.py`):**
- Магазин целиком: выручка и прибыль по дням — P&L по дням (`pnl_service.get_by_day`, прибыль до налога), итоги — P&L
  периода (`get_pnl`): выручка = `revenue_base`, прибыль = `net`, если налог есть в обоих сравниваемых периодах, иначе
  `profit_before_tax` (`profit_kind`), маржинальность = прибыль / выручка × 100 — совпадает с маржой P&L. Налог по дням не
  делится, поэтому в точках ряда прибыль — до налога, и сумма точек = прибыль до налога P&L.
- Товар, несколько товаров, категория: тот же движок, что «Прибыль по товарам» (3.4) — по дням и за период; итоги
  совпадают с этой страницей: прибыль — до налога, только по товарам с себестоимостью, маржинальность = прибыль / выручка
  этих товаров. Товар без себестоимости — `missing_cost` (правило 5). День с начислениями без продаж товара — 0, день
  без начислений — пропуск.
- Продано, возвращено (шт.), возвраты (₽) — `sales_daily`; заказы — отправления по дню заказа без `cancelled*` и
  `not_accepted`, заказ — отправление, в котором есть товар фильтра, штуки — позиции этих товаров. День загружен, если он в
  окне загруженных отправлений (`posting_syncs`: с `loaded_from` по день последней синхронизации).
- Точка ряда — сумма дней с данными; ни одного — пропуск; `missing_days` / `orders_missing_days` — сколько дней без
  данных; неделя (пн–вс) или месяц, обрезанные краем периода, — `partial`. Средняя цена = выручка / проданные штуки.
  Изменение к прошлому периоду — %, у маржи — п. п.; прошлое значение 0 или неизвестно — сравнения нет. Точки прошлого
  периода — по порядку (первая неделя с первой неделей).
- Эталон (неделя 07–13.09.2026): начисления 07, 08, 10 — выручка 1500, 500, —, 600, —, —, —, итого 2600 = P&L; продано
  5 шт., средняя цена 520; заказы 1, 0, 0, 0, 0, 0, — (13.09 отправления не загружены); товар A 07.09: 1000 − 200 −
  100 × 2 = 600 прибыли.

### «Обзор бизнеса»: лучшие и худшие товары (шаг 10.7)
- **По прибыли** — прибыль товара за период из «Прибыли по товарам» (3.4, до налога): лучшие — прибыль больше нуля, по
  убыванию; худшие — из остальных, по возрастанию (в минусе — первыми); по 5. Товары без себестоимости не участвуют —
  их число показываем отдельно со ссылкой «Заполнить» (правило 5).
- **По изменению продаж** — проданные штуки (`sales_daily`) за дни с данными против прошлого сопоставимого периода:
  ожидали = продано тогда / дней с данными тогда × дней с данными сейчас. Рост или падение — только значимые, порог шума
  как в аномалиях §7: у Пуассона с ожиданием «ожидали» вероятность такого числа меньше 1 %. Не продавалось — рост «с
  нуля» (ожидание не меньше 0,5 шт., значит от 4 шт. за период); процент — к ожидаемому. Меньше 7 дней с данными в
  одном из периодов — не сравниваем. Порядок — по изменению в штуках; по 5.
- Фильтр категории или нескольких товаров — лидеры среди них; один товар — лидеров нет (его статистика — 10.14).
- Эталоны (`tests/test_analytics_overview.py`): 100 → 40 шт. — падение −60 %; 8 → 0 — падение; 10 → 30 — рост +200 %;
  2 → 3 и 0 → 3 — шум; 0 → 5 — рост с нуля; 10 шт. за 15 дней против 40 за 30 — ожидали 20, +100 %.

### «Аналитика продаж» (шаг 10.8)

  пропускаем), «через сервис» — если в тот же день сервис применил именно эту цену; **акция** — вход и выход (участие 4.3,

- Эталоны (`tests/test_analytics_sales.py`): X — 10 заказов по 2 шт. (2 отмены не считаются), 60 шт. на 6000 ₽, средняя

### «Требует внимания» (шаг 10.5)
- Источник — аномалии (§7) плюс проверки состояния данных: ошибка последней синхронизации (по виду данных), дни без
  начислений за период, товары с продажами без себестоимости, отчёты с ошибкой разбора, избыток запаса (статус
  «Избыток», §6 / 5.1).
- Порядок — важность (красная → жёлтая → к сведению), внутри — деньги под риском, ₽, где их можно оценить (убыток в акции,
  недополученная выплата, стоимость лишнего запаса), затем — новые первыми.

**Как сделано (шаг 10.5, `engine/anomaly_detector.py`, `services/anomalies.py`, эталоны — `tests/test_attention.py`):**
- «Требует внимания» — это активные аномалии без «Ок» (одни и те же на главной, в колокольчике, в «Уведомлениях» и в
  Telegram); проверки данных — новые типы аномалий, проверяются вместе с остальными раз в час. «К сведению» пока не
  понадобилось: каждый пункт просит действия — красная или жёлтая.
- **Синхронизация** (группа «Данные», по видам окна «Синхронизация» 10.2): само не пройдёт — ключ Ozon не принят, нет
  прав, ключа нет, банк не принял токен — красная сразу; одна причина у нескольких видов Ozon — один пункт («данные Ozon не
  обновляются»). Остальное (Ozon или банк не отвечает, давно не обновлялось, ещё не загружалось) — жёлтая, только если
  данных нет дольше порога (24 ч, настройка) от последней удачной загрузки, а у не загружавшихся — от подключения ключа
  или банка: разовый сбой и первые часы после подключения не тревожат. Идёт загрузка — не судим. Ключа никогда не было
  (только отчёты) — проверять нечего.
- **Пропуски начислений:** за последние 30 дней (до вчера) — дни без начислений между первым и последним загруженным
  днём; от порога (1 день, настройка) — жёлтая со списком промежутков. Хвост после последнего загруженного дня — не
  пропуск: отчёт ещё не вышел, а если не грузит ключ — это пункт синхронизации. Загруженных дней нет — не судим.
- **Отчёт с ошибкой** — отчёт XLSX со статусом «ошибка» (не удалось перечитать, 2.2), не скрытый: жёлтая на отчёт,
  закрывается, когда перечитали или скрыли.
- **Продажи без себестоимости** — за 30 дней продажи в дни без себестоимости по справочнику на день продажи (как P&L);
  дни без начислений не считаются (продажи неизвестны). Один жёлтый пункт на все товары: сколько товаров, выручка, 5
  крупнейших; ссылка — «Себестоимость» с фильтром «без себестоимости».
- **Избыток запаса** (группа «Остатки») — статус «Избыток» 5.1, жёлтая; лишнее = `остаток − ⌈продажи в день × порог⌉`
  (не продаётся — весь остаток), как «На вывоз» (§6).
- **Деньги под риском** (`money_at_risk`, ₽, только больше нуля): убыток в акции = −маржа × цена акции × продажи в день ×
  дни до конца акции (не больше 30; конец неизвестен — 30); маржа ниже нуля при текущей цене — убыток за 30 дней;
  выплата не пришла — ожидаемая сумма; пришла меньше прогноза — недостача (больше — не риск); не дошла до счёта — сумма
  выплаты, пришло меньше — разница; кассовый разрыв — сколько не хватит до нуля (до порога остатка у жёлтой); избыток —
  лишнее × себестоимость с НДС. Не продаётся или нет себестоимости — оценить нельзя (null), а не 0. Это оценка «сейчас»:
  каждая проверка её обновляет; у сводных пунктов (продажи без себестоимости, пропуски, синхронизация, операции без
  статьи) — и цифры текста; было / стало у остальных — на момент обнаружения.
- Порядок (`/anomalies`, order=severity — по умолчанию у активных): красные → жёлтые, внутри — больше денег под риском
  (без оценки — после), затем новые. Главная — первые 7 и «И ещё N».
- Эталоны: избыток 300 шт. при 2 шт. в день и пороге 60 дней — лишнее 180 шт. × 100 ₽ = 18 000 ₽; не продаётся 10 шт. ×
  50 ₽ = 500 ₽; убыток в акции −10 % × 1000 ₽ × 2 шт. × 5 дней = 1000 ₽; маржа −5 % × 1000 ₽ × 1 шт. × 30 = 1500 ₽;
  выплата 8500 при прогнозе 10 000 — 1500 ₽; разрыв −3000 — 3000 ₽, остаток 8000 при пороге 10 000 — 2000 ₽.

### «Рекомендуемые действия» (шаг 10.6)
- Рекомендация появляется, только если данных хватает: продажи — не меньше 14 дней с данными за 30, есть цена, есть
  себестоимость (кроме рекомендации «заполнить себестоимость»). Иначе — не показываем (а не «примерно»).
- У каждой — почему появилась (условие и цифры) и на каком расчёте основана (калькулятор цены §4, поставки §5, вывоз §6).
  Примеры: цена ниже минимальной по калькулятору → «проверить цену»; поставка «Срочно / Скоро» (§5) → «запланировать
  поставку»; продажи без себестоимости → «заполнить себестоимость»; акция с отрицательной маржой → «выйти из акции».

**Как сделано (шаг 10.6, `engine/recommendations.py`, `services/recommendations.py`, эталоны — `tests/test_recommendations.py`):**
- Данных хватает: за последние 30 дней (до вчера) не меньше 14 дней с начислениями — иначе ни одной рекомендации (на
  главной — «Советы появятся, когда наберётся 14 дней…»). По товару — только если есть цена Ozon и себестоимость на
  сегодня; «заполнить себестоимость» — без этого условия. Поставкам нужны ещё 14 дней отправлений (FBO — поставки, FBS —
  закупки).
- Правила и порядок: **акция в минус** (самая низкая цена товара в текущих акциях, маржа калькулятора ниже нуля) →
  **цена ниже минимальной** (калькулятор 4.2) → **поставка «Срочно»** → **«Скоро»** (5.2, одна рекомендация на товар:
  самое срочное направление, всего штук и направлений) → **заполнить себестоимость** (продажи за 30 дней в дни без
  себестоимости — одна на все товары, по товару — своя) → **вывоз** (кандидат «На вывоз» без продаж за 30 дней). Внутри
  правила — больше денег на кону, у поставок — меньше дней запаса, затем по артикулу.
- Деньги на кону: акция — убыток с штуки × продажи в день × дни до конца акции (не больше 30; конец неизвестен — 30);
  цена — убыток с штуки при текущей цене × продажи в день × 30; вывоз — к вывозу × себестоимость с НДС. Не продаётся —
  не оцениваем. У поставки и себестоимости денег не показываем.
- У каждой: что сделать, почему (цифры), на каком расчёте (название страницы, где его видно), кнопка действия.
  «Скрыть» — на N дней (настройка магазина, 7), каждое нажатие — новая запись, «Вернуть скрытые» — отмена; «Сделано» не
  отмечается — условие ушло, рекомендация исчезла.
- Эталоны: цена 900 при минимальной 1050, с штуки −40,50 ₽, 2 шт. в день — 2430 ₽ за 30 дней, +16,7 % до минимальной;
  акция 800 ₽ при марже −6 % — минус 48 ₽ с штуки, 1 шт. в день, 5 дней — 240 ₽; вывоз 100 шт. × 300 ₽ — 30 000 ₽;
  поставка: «Москва» 3,5 дн. (критично) и «Санкт-Петербург» 10 дн. — 45 шт., 2 направления.

### ABC-анализ (шаг 10.10)
- Товары за период сортируются по критерию (выручка / прибыль / продажи, шт.) по убыванию; накопленная доля от суммы:
  **A** — до 80 %, **B** — до 95 %, **C** — остальное (границы — настройка). Для прибыли товары с нулём и убытком — в C и
  отдельной пометкой «убыточные»; доля считается от суммы положительной прибыли.
- Сравнение ABC по выручке и прибыли — матрица 3 × 3 (например, «A по выручке, C по прибыли» — продаётся много, но
  зарабатывает мало).

### Запасы (шаги 10.17, 10.18)
- **Скорость продаж** = продажи, шт., за 30 дней / дни с данными (как `avg_daily`, §5). **Прогноз даты окончания** =
  сегодня + остаток / скорость; продаж нет — «не продаётся», а не дата.
- **Стоимость запаса** = остаток × себестоимость с НДС на сегодня (справочник 2.3); нет себестоимости — «нет данных»,
  товар — в «Требует внимания», не 0 (правило 5).
- **Замороженные деньги** (на вывоз) = рекомендованное к вывозу количество × себестоимость с НДС.
- **Страховой запас**, дни — добавляется к целевому запасу поставки (`target_days`, §5), по умолчанию 0.

### Бюджеты и сценарии (шаг 10.21)
- План — сумма по статье и периоду (месяц; квартал и год — сумма месяцев). Факт — операции по статье за период
  (подстатьи входят в статью), переводы между своими счетами не считаются (как в ДДС 3.10).
- Отклонение = факт − план, % = отклонение / |план|. Для доходов хуже плана — меньше, для расходов — больше.
- Сценарии — множители к плановым доходам и расходам: базовый — ×1; оптимистичный и пессимистичный — пользователь
  задаёт свои (по умолчанию доходы +10 % / −10 %, расходы −5 % / +10 %). Прогноз остатка и разрыва по сценарию — тем же
  расчётом, что прогноз 3.10.

### Календарь и ДДС (шаг 10.24)
- Статус платежа: **запланирован** — дата в будущем; **ожидается** — дата сегодня или прошла не больше чем на 3 дня
  (банк ещё может не показать); **оплачен** — есть факт на всю сумму; **частично оплачен** — факт меньше плана;
  **просрочен** — дата прошла больше чем на 3 дня, факта нет.
- Прогноз кассового разрыва: первая дата, когда прогнозный остаток < 0 (или ниже порога пользователя); нехватка —
  минимальный остаток на горизонте; причины — крупнейшие расходы до этой даты и не пришедшие ожидаемые поступления.
