# Что сделано по шагам — подробности

Подробности реализации завершённых шагов: файлы, решения, отличия от промпта. Статус шагов — в `CLAUDE.md`,
план — в `docs/ROADMAP.md`. Открывай нужный раздел, когда шаг опирается на сделанное раньше.

После каждого шага сюда добавляется раздел `## X.Y — название` (решения, файлы, API, что переиспользовать).

## 0.2 — Авторизация на бэкенде (JWT, register/login/refresh/logout/me)

access-токен 24 ч, refresh 30 дней; refresh одноразовый
(ротация); logout отзывает токены через чёрный список в Redis (в тестах — в памяти);
ошибки валидации отдаются как 400 с русским текстом.

## 0.3 — Авторизация на фронтенде (httpOnly cookies, /login, /register, /dashboard)

токены живут только в httpOnly cookies (`access_token`,
`refresh_token`), JS браузера их не видит. Браузер ходит к бэкенду через route
handlers Next: `/api/session/{login,refresh,logout}` ставят/чистят cookies,
`/api/session/proxy/<путь>` → `<API>/api/v1/<путь>` с `Authorization` из cookie
(методы выдачи токенов через прокси закрыты). Адрес бэкенда для сервера Next —
`API_URL` (в Docker `http://api:8000`), иначе `NEXT_PUBLIC_API_URL`.
`src/lib/api.ts` — axios: при 401 один общий refresh и повтор, иначе `/login?next=…`.
`src/middleware.ts` пускает на `/dashboard/*` только при наличии cookie сессии.
В nginx на бэкенд проксируется только `/api/v1/`, остальное `/api/*` — Next.

## 0.4 — Хранение API-ключей Ozon (шифрование, /dashboard/settings/api-keys)

таблица `api_credentials` (миграция 0002), Api-Key — только
Fernet-шифротекст (`services/encryption.py`; ключ проверяется в lifespan при старте).
`services/ozon_auth.py` проверяет ключ запросом `POST /v3/product/list` (limit=1):
401/400/404 → неверные ключи, 403 → нет прав (или «ключ отключён/истёк» по тексту Ozon),
429/5xx/сеть → Ozon недоступен. `/api/v1/credentials`: POST сохраняет только принятый
Ozon ключ (иначе 400, при недоступности Ozon — 503), GET — без ключа, Client-Id как
`••••1234`, DELETE и POST `/{id}/verify` (invalid/forbidden → `is_active=false`,
недоступность Ozon состояние не меняет). Чужой ключ — 404. Срок ключа берётся из Ozon
(`POST /v1/roles` → `expires_at`) при добавлении и каждой проверке; если Ozon его не
сообщил — введённый пользователем или +3 месяца (срок ключа по документации Ozon);
`days_until_expiry` считает бэкенд, фронт предупреждает при < 30.
Тест `test_api_key_never_returned_or_logged` ловит ключ в ответах и логах (DEBUG).
Сверено с официальной документацией (`docs/ozon/`): проверка — `/v1/roles`, затем
`/v3/product/list` (limit=1); тексты ошибок ключа распознаются по «Частым ошибкам» Ozon.

## 1.1 — Универсальный клиент Ozon (retry, rate limit, фабрика)

(`app/integrations/ozon/`): все запросы к Ozon — только через
`OzonClient.request(method, path, json)`; перед каждой попыткой клиент берёт слот в
rate limiter: 50 запросов/с на Client ID (документация Ozon) плюс `METHOD_LIMITS` для
методов со своим лимитом.
Повторы: сеть/таймаут — 3 повтора (1, 2, 4 с); 429 — до 6 повторов (Retry-After ≤ 60 с
или 1…30 с); 5xx — 2 повтора через 5 с; 401/403/прочие 4xx — сразу исключение.
Иерархия: `OzonAPIError` → `OzonAuthError`, `OzonRateLimitError`, `OzonServerError`,
`OzonTimeoutError`, `OzonNetworkError`, `OzonNotConfiguredError`; у ошибки есть
`status_code`, `ozon_message` (ключ вырезан), `path`; у `OzonAuthError` — `kind`
(invalid / deactivated / no_role / ip_restricted / forbidden, по текстам Ozon);
«Circle is open» — `OzonServerError` без повторов. Rate limiter — скользящее окно в
Redis (sorted set + Lua, атомарно для API и всех воркеров), без Redis — в памяти. `get_ozon_client(user_id, db)` берёт активный
неистёкший ключ (последний использованный), обновляет `last_used_at`, клиент закрывать
(`async with`). Проверка ключа из 0.4 (`services/ozon_auth.py`) работает через тот же
клиент без повторов. Тесты лимитера против реального Redis: `TEST_REDIS_URL=redis://… pytest`.

## 1.2 — Синхронизация товаров и цен (Celery, Beat, /sync, статус в шапке)

миграция 0003 — `products` (уникальность user_id+ozon_product_id),
`product_prices` (снепшоты) и `sync_runs` (журнал запусков: queued → running →
success/failed; нужен для статуса и защиты от двойного запуска, зависший > 30 мин

`/v5/product/info/prices` (cursor); снепшот цены — только при изменении полей.

пишутся в `sync_runs.error`, наружу не летят; новые виды синхронизации добавляются
в `JOBS`. Celery (`app/tasks/sync.py`): `sync_products_for_user`, `sync_products_all`
(Beat, каждый час в :07) ставит отдельную задачу на каждого пользователя с
действующим ключом. В задачах свой движок БД с NullPool (новый event loop на запуск).
В Docker Compose добавлен сервис `beat`. API: `POST /api/v1/sync/products` (202,
409 если уже идёт, 503 если брокер недоступен), `GET /api/v1/sync/status`.
Фронт: `components/SyncStatus.tsx` в шапке кабинета. Тестовые ответы Ozon —
`backend/tests/fixtures/ozon/*.json` (только `total_items`). Разбор полей сверен с
документацией — таблица в `docs/OZON_API.md` («Как мы читаем ответы»).

## 1.4 — Финансовые начисления из API (by-day + postings, Celery, /finance)

(схема согласована с владельцем): миграция 0005 — `accrual_types`

`GET /api/v1/finance/accruals/by-day` (+ missing_periods), `POST /api/v1/finance/sync`;

`services/stocks.avg_daily_sales` к начислениям пока не подключён — продажи из API есть по
товарам, но не по складам; подключается на шаге 3.5 (продажи по дням).

## 2.1 — Парсер XLSX-отчётов Ozon (детектор, начисления, реализация, POST /reports/parse)

(`app/integrations/xlsx/`): `parse_report(content, costs, filename)` →
`schemas/report.NormalizedReportData` (+ sheet_name, header_row с 1, rows_count; суммы — Decimal,
в JSON строкой). `common.py`: чтение книги (openpyxl read_only + data_only, `reset_dimensions`,
.xls распознаётся по сигнатуре), `norm` (переносы/NBSP/пробелы, нижний регистр, ё→е),
`parse_number` (пробелы, ₽/руб., запятая/точка, «−», скобки; пусто → None; нечитаемое → None и
предупреждение с номером строки; > 20 таких — сворачиваются), `extract_period`. `detector.detect`
— сигналы и уверенность как в эталоне (60 строк каждого листа), «показной» ищется и выше заголовка,
имя файла — только при равной уверенности. Парсеры `parsers/accrual.py`, `parsers/realization.py`
— логика `reference/ozon_calculator.html`; учёт товаров и себестоимости — `parsers/base.SalesLedger`
(неизвестный артикул → missing_cost, cost=None, в cost_sales не входит, предупреждение; строки без
артикула — предупреждение). Отличия от эталона (баги/ручные данные): период реализации — из
«…за период с … по …», а не из «Отчет … от <даты>»; строки начислений без «Тип начисления» (ручные
пометки под таблицей) в auto_total не входят — предупреждение; итог реализации берётся и при ≤ 0;
строка нумерации столбцов не считается товаром. Нет «Всего выплат от партнёров» — предупреждение
и 0 (как в эталоне), нет «Итого реализовано» — сумма строк и предупреждение. Себестоимость —
`integrations/xlsx/costs.CostProvider` (`cost_of(article)`); с шага 2.3 `services/costs.get_cost_provider`
даёт справочник пользователя из БД (CSV-настройка `COST_PRICES_CSV` убрана). API: `POST /api/v1/reports/parse`
(multipart `file`, ≤ `REPORT_MAX_SIZE_MB` → иначе 413, ошибки разбора — 400 с русским
текстом), без сохранения. P&L (owed, налог, net) — шаг 3.1.

## 2.3 — Справочник себестоимости (история цен, импорт CSV/XLSX, /dashboard/costs, пересчёт отчётов)

миграция 0009 — `product_costs` (user_id, offer_id, cost_price без НДС,
vat_multiplier — NULL = «как в основных настройках», effective_from, note, source

(`services/report_costs.cost_date`). Итоги отчётов — производные: после изменения цены
`recost_reports` пересчитывает summary_json видимых отчётов с этими артикулами (повтор
`SalesLedger` по by_article, без перечитывания файла; предупреждения «Не найдена себестоимость»

## 3.1 — P&L engine (остаток, налог по профилю, маржа; эталоны до копейки) и P&L в отчётах

`app/engine/pnl.py` — `PnLEngine.compute(data, PnLParams)` → `PnLResult` (auto/effective
total, revenue_base, cost_sales, owed, profit_before_tax, tax, vat, tax_lines, net, margin, pct_of_revenue, by_type,
by_type_pct, missing_cost, warnings, data_source) и `validate` (`PnLIssue`: no_revenue, no_items, missing_cost,
owed_too_big — себестоимость с НДС > суммы от Ozon × 3). owed = Σ цена × шт. × НДС поставщика (свой у артикула из
справочника, иначе по умолчанию). Налог и НДС — из `engine/tax.compute_tax` (профиль на дату периода); нет профиля —
tax, vat, net, margin = None и предупреждение `TAX_NOT_SET`. Округление один раз, в конце: `TaxResult` теперь отдаёт и
`tax_exact`/`vat_exact` (эталон реализации 15 910,23, а не 15 910,22). by_type_pct — доходы от суммы положительных,
расходы от суммы отрицательных, каждая группа ровно 100,00 (остаток округления — самым большим дробным частям).
`services/report_pnl.py`: `load_context` (профили + себестоимость, один раз на запрос), `report_pnl` — профиль на дату
начала периода; поправка отчёта tax_rate (+ tax_base) — «Свой процент» только для него; vat_multiplier отчёта — НДС
поставщика для артикулов без своей ставки; manual_total. `profile_title` перенесён в `services/tax_profile`. API: у
отчётов (список, детали, загрузка, PATCH, restore, reparse) поле `pnl` (`schemas/report.PnLOut`), `/reports/parse`
отдаёт `ParsedReport` (данные + pnl). Фронт: `ReportFigures` — 5 плиток (продано, пришло от Ozon, себестоимость с
НДС, налог или «налог и НДС» / «не задан» со ссылкой, остаток с маржой), `PnLBreakdown` — расчёт по шагам с % от
выручки и «Как посчитан налог», `ByTypeTable` — доли в группе; «налог не задан» в списке предупреждений не
повторяется (`pnlWarnings`).

## 3.2 — P&L API за любой период (XLSX / API по дням, кэш 5 мин, снимки закрытых месяцев)

P&L за период считается из строк начислений по дням (`services/pnl_data.py`): `coverage` —
источник каждого дня: xlsx — дни, которые покрывает видимый отчёт по начислениям (весь его период; отчёты пересекаются
— за день берётся загруженный позже), api — дни из `accrual_days`, auto — XLSX, если есть, иначе API, иначе нет данных
(пропуск, а не 0). Отчёты о реализации по дням не делятся и в P&L периода не входят (предупреждение). `build` собирает
строки в `NormalizedReportData`: себестоимость — по строкам «Выручка» с артикулом на дату строки (у API артикул — из
товара), НДС артикула — средний по строкам; дальше тот же `PnLEngine`, что у отчёта (налог — по профилю на начало
периода; профиль менялся внутри — предупреждение). Ручная сумма отчёта применяется, если отчёт целиком внутри периода
и все его дни взяты из него. Неделя эталона из строк = отчёт (−1 419,07). `services/pnl_service.py`: `PnLRequest`
(период ≤ 366 дней, source, vat_multiplier, tax_rate + tax_base — «свой процент» для расчёта, manual_total),
`get_pnl`, `get_by_day`, `get_periods`. Кэш — `services/pnl_cache.py`: Redis (общий для API и воркеров, клиент на
цикл событий), без Redis — память; ключ `pnl:<user>:<версия>:<вид>:<sha1 параметров>`, TTL 300 с, сброс — увеличение
версии пользователя. Миграция 0011 — `pnl_snapshots` (user, период, source, data_json = ответ /pnl, calculated_at,
stale, stale_reason, stale_since): закрытый календарный месяц без своих параметров сохраняется при первом запросе и
отдаётся из снимка (`from_snapshot`), устаревший — пересчитывается. `services/pnl_stale.invalidate` (в той же
транзакции, что и изменение) помечает снимки, чей период задет, и сбрасывает кэш: загрузка, замена, скрытие,
восстановление, перечитывание и PATCH отчёта — его период; себестоимость (PUT, импорт) и налоговый профиль — период
действия новой записи (`affected_period`); синхронизация начислений — загруженный день. API: GET `/api/v1/pnl`
(date_from — по умолчанию начало месяца, date_to — сегодня; ответ: source, data_source xlsx|api|mixed|none, coverage
с пропусками, reports, auto_total, by_type, missing_cost, pnl = PnLOut отчёта или null, warnings, calculated_at),
`/pnl/by-day` (выручка, начисления, себестоимость с НДС, прибыль до налога; нет данных — null), `/pnl/periods`
(отчёты, дни API, покрытие по месяцам и состояние снимков). `report_pnl.to_out` — общий PnLOut для отчётов и периода.
Страницы нет — «Финансы» на шаге 3.3.

## 4.3 — Акции: история участия, вход и выход через Ozon, карточки, страница акции

Откат миграции удаляет прошлые участия — они не помещаются в старую уникальность.

Синхронизация (`services/sync/promotions.py`): участник, которого не было, — новая строка (кандидат той же пары
удаляется) и снимок; у участника сменилась цена или количество — снимок; пропал из участников — `left_at`, строка

окончания (или временем синхронизации, если она ещё не наступила), кандидаты удаляются. В статистике — `entered`,
`left`, `price_changes`. Все «текущие» запросы (API акций, `pricing.current_promotions`) берут только `left_at IS NULL`.

История — `services/promotion_history.py`, GET `/api/v1/promotions/history` (product_id — необязательно; date_from /
date_to — дни по Москве, по умолчанию 90 дней, не больше 366): участия, пересекающиеся с периодом, новые первыми —
акция, вход, выход (или окончание акции), статус active | left | ended, цена в акции со всеми снимками, обычная цена,

## 6.3 — Массовое изменение цен (стратегия или Excel, предпросмотр по группам, по 100 в Ozon с ходом по запросам)

Правила и как сделано — BUSINESS_LOGIC §8 «Массовое изменение цен». Решения шага (не владельца, по умолчанию): товары с
предупреждениями в применение не входят, пока их не включили галочкой; «не больше 20 % за раз» у стратегии включено —
цена дальше допустимого становится ближайшей допустимой (выключить — такие товары блокируются).

Миграция 0026 — `price_changes.batch_id` (общий id предпросмотров одного массового изменения, индекс) и `batch_no`
(номер запроса в Ozon по 100 товаров). Новый итог `queued` — в очереди на отправку; `REACHED_OZON` (applied, unknown,
queued) считается часовой паузой (`price_safety.last_changes`). `price_safety.allowed_range(PriceCheck)` — что можно
поставить за один раз (для стратегии). Из `price_updater` (6.2) стали общими: `fresh_prices` (цены многих товаров одним
запросом, снимки при изменении), `margins`, `auth_text`, `ozon_failure`, `ozon_reasons`, `result_for`, `state`; одиночное
применение не принимает предпросмотр из массового изменения (400 «примените его на странице „Цены списком“»).

`services/price_bulk.py`: `Strategy(kind, value, limit_step)` (target_margin — `calc.price_for_margin`, percent —
текущая × (1 + X %), min_plus — минимальная × (1 + X %); `describe()` — в причину изменения), `strategy_items`;
`preview` — до 500 товаров, свежие цены (Ozon недоступен — по снимкам с предупреждением, нет ключа — 400), проверки
`PriceSafetyChecker` по каждому + архив и «Ozon не вернул цену», группы ok / warn / blocked (применится — первыми),
не меняющиеся — `unchanged`, записи preview с общим `batch_id`, маржа и «с 1 шт.» было / станет; `apply` — по batch_id:
не применялся (409), не старше 15 минут (410), есть что применять (400), `check_request` (больше 10 — confirmed,
больше 50 — слово), свежие цены (не получили — 502, ничего не меняли), блокировка строк товаров, проверки заново
(изменилась цена или ошибки — blocked и журнал rejected), остальные — queued с `batch_no` (по артикулу) и коммит
(уникальный preview_id), затем запросы по 100 (`_send`: «отправляется» = unknown без текста ошибки → итог каждого товара,
журнал со своей частью запроса и ответа и номером запроса, снимок применённой цены) с паузой `BATCH_PAUSE_SEC` (2 с);
ошибка запроса — failed / unknown только у его товаров; `status` — по товарам (applied / rejected / failed / unknown /

## После запуска на сервере (20.10.2026) — начисления Ozon API по реальному формату

Владелец: на главной нет продаж за текущий месяц. Диагностика на сервере (запросы к Ozon из контейнера api, без
изменения данных): первая загрузка начислений упала через секунду — `/v1/finance/accrual/postings` ответил 400 «value
does not match regex pattern ^[0-9]+-[0-9]+-[0-9]+$»: у части записей by-day `unit_number` — номер заказа
(`1234567890-0001`) или поставки (`RU12-AB123456789`), а не отправления. Справочник типов отдаёт английский код в `name`
и русское название в `description`, а типа «Выручка» в нём нет вовсе: выручка, баллы и программы партнёров приходят в
записи отправления (`posting.products[].commission`). Соответствие сверено с отчётом XLSX владельца на трёх отправлениях
копейка в копейку (OZON_API.md, «Начисления»).

`services/sync/finance.py`: строки — только из `/v1/finance/accrual/by-day` (`parse_entry`): POSTING — «Выручка» =
`sale_amount − bonus − coinvestment` (отрицательная — «Возврат выручки»), «Баллы за скидки» = `bonus`, «Программы
партнёров» = `coinvestment`, «Вознаграждение за продажу» = `commission`, доставка — `delivery.services` по типу; ITEM —
`item_fees` по товару; NON_ITEM — `non_item_fee`, `container_fees`; иначе — `total_amount`. Суммы продажи — служебные
типы с отрицательным id (`VIRTUAL_TYPES`, названия как в отчёте XLSX) — их видят P&L, прибыль по товарам, продажи по дням,
список начислений. `unit_number` → `posting_number` («ID начисления», как в XLSX). Область — `day:<дата>`. Сумма строк
записи сверяется с `total_amount` (`is_balanced`; не сошлось — `stats.unbalanced` и предупреждение в журнале: формат Ozon
изменился). `/postings` не используется (неполный — нет эквайринга, только номера отправлений, маленький лимит в
секунду). Справочник: `code` — английский код, `name_ru` — русское название из `description`.
Миграция 0031: `accrual_types.code`, перенос кода и русского названия в существующих строках, удаление строк прежнего
разбора по отправлениям (`posting:*`, `posting-day:*`) и сброс `accrual_days` — следующая синхронизация перезагружает
начисления за 90 дней (копии данных Ozon; отчёты XLSX не затрагиваются).
`services/sync/runner.ozon_error_text`: общий отказ Ozon в журнале запусков и в шапке сайта — с методом и текстом Ozon
(«Ozon отклонил запрос (HTTP 400) — /v1/finance/accrual/by-day: …»), ошибки ключа — как были. `pnl_cache.aclose` в конце
каждой задачи Celery (`tasks.task_sessions`) — клиент Redis закрывается в своём цикле событий, без «Event loop is closed»
в журнале воркера.

Тесты (678 всего; `test_sync_finance.py`, фикстуры — формат реальных ответов, номера и суммы выдуманы, `accrual_postings.json`
удалён; запрос к `/postings` уронил бы тест): разбор всех видов записей и сумма дня, соответствие отчёту XLSX, 2 шт. в
строке, возврат, запись без блоков, несошедшаяся сумма, русские названия и служебные типы, заглушка неизвестного типа,
без дублей, P&L / продажи по дням / выручка на главной по данным API, текст ошибки Ozon в запуске, закрытие клиента кэша.

## Шаг 8.4b — несколько магазинов у одного аккаунта (22.10.2026)

Запрос владельца: два API-ключа у одного человека — товары разных магазинов смешивались. Причина: все данные привязаны к
`users.id`, а фабрика клиента Ozon брала последний использованный ключ, так что ключи двух кабинетов писали в одни таблицы.

**Модель.** Магазин — строка `users` без входа: `owner_id` (аккаунт человека, FK users, CASCADE), `store_name`,
`ozon_client_id` (кабинет Ozon; задаёт первый ключ). Первый магазин — сам аккаунт (`owner_id IS NULL`): существующие
данные на месте, код данных не менялся — он по-прежнему работает с одним `user_id`. `User.account_id` — аккаунт магазина.
`email` и `hashed_password` стали необязательными (у магазина пусто); войти магазином нельзя — `get_current_user`
отклоняет строку с `owner_id`.

**`services/stores.py`.** `get_current_store` — зависимость всех эндпоинтов данных (24 роутера и `services/costs`): заголовок
`X-Store-Id`; нет или равен аккаунту — первый магазин; чужой, отключённый, не UUID — 404 «Магазин не найден». Ставит
`request.state.audit_user_id` — middleware журнала пишет запрос на магазин. `working()` — условие фоновых задач (магазин
включён и аккаунт владельца не закрыт): `tasks.users_with_active_keys`, `users_for_anomalies`,
`bank_connections.users_with_connections`. `check_key_for_store` — один магазин, один кабинет: ключ другого Client-Id — 409
(«добавьте его отдельным магазином»), кабинет уже в другом магазине аккаунта — 400; магазин без ключей и товаров может
сменить кабинет. `new_store_name` / `create`, `rename` (название уникально в аккаунте), `set_active` (первый магазин не
отключить), `overview` (название, кабинет — маска, ключи и работающие, уведомления без «Ок»), `names`, `store_ids`,
`accounts_for`, `account_of`. Лимит — 20 магазинов на аккаунт (тарифы 8.1 сделают его по тарифу).

**API.** Аккаунт (`get_current_user`): `GET /stores`, `POST /stores` (Client-Id, Api-Key, название; проверки до Ozon →
проверка ключа в Ozon → магазин и ключ одним коммитом → в очередь товары, остатки, акции, начисления, баланс, отправления),
`PATCH /stores/{id}` (название, `is_active`). `POST /credentials` — правило кабинета, первый ключ задаёт кабинет.
`/settings`: тема — у аккаунта, остальные поля — у магазина. `/auth`, `/notifications` — аккаунт.

**Уведомления.** Аномалия и запись `notification_log` — магазина, настройки и чат — аккаунта (`stores.account_id`).
`send_due` группирует ожидающие по аккаунту — одно сообщение на всех магазинах; у аккаунта с несколькими магазинами у
каждой строки — название магазина, ссылка — с `?store=<id>` (`engine.notifications.Item.store`, `store_id`). Отключение
Telegram, «последнее отправленное», «ожидают» — по всем магазинам аккаунта. Бот `/status` — по каждому магазину.

**Уже смешанные данные.** Миграция 0032: у аккаунта с ключами нескольких Client-Id ключ самого раннего остаётся у аккаунта,
ключи каждого другого переносятся в новый магазин (название — название ключа или «Магазин N»; ключи не расшифровываются),
отметки «день загружен» начислений такого аккаунта сбрасываются (следующая синхронизация заменит строки API ключом своего
магазина), `ozon_client_id` — по самому раннему ключу. Откат возвращает ключи аккаунту и удаляет строки магазинов.
`services/sync/products.archive_gone` — товары, которых нет в кабинете ни в одном статусе, — в архив (не удаляются; пустой
ответ Ozon не архивирует ничего; вернулся — архив снимается), `ProductSyncStats.gone`. Команда администратора
`resync EMAIL` — каждому работающему магазину аккаунта с действующим ключом в очередь товары, остатки, акции, отправления,
начисления и баланс за 90 дней (явный период: дни перезагружаются). `admin users` — только люди, с числом магазинов.

**Интерфейс.** `contexts/StoreContext.tsx` (`StoreProvider` в `dashboard/layout`, `useStores`, `openStore`): список
`/stores`, текущий — cookie `store_id` (не секрет, обычная cookie), переключение — cookie и перезагрузка той же страницы без
параметров; `?store=<id>` (ссылка из Telegram) открывает магазин и убирает параметр; отключённый или чужой магазин в cookie
— сброс к первому. Прокси Next передаёт cookie заголовком `X-Store-Id` (только UUID); вход и выход стирают выбор
(`clearStoreCookie`). `components/StoreSwitcher.tsx` — полоса «Магазин: …» под шапкой, только при двух и более включённых
магазинах (в шапке места нет уже на 1024 px): список с кабинетом и числом уведомлений без «Ок», «Все магазины и добавить
новый →», справа — «В других магазинах уведомлений: N». Страница `/dashboard/settings/stores` («Магазины» в меню аккаунта):
что у магазинов своё, а что общее; список — открыть, переименовать, отключить (с пояснением, что будет) и вернуть;
«Добавить магазин» с ключом. «API-ключи Ozon» — чьи это ключи и правило кабинета; ключ другого кабинета — ошибка и кнопка
«Добавить отдельным магазином» (тот же ключ → новый магазин → переход в него).

Решения: планирование, налоговый профиль, банки, себестоимость, настройки (кроме темы) — у каждого магазина свои (у разных
магазинов бывают разные юрлица и условия); профиль, пароль, тема, Telegram — общие. Магазины не удаляются (правило 12).

Тесты (690 всего; `test_stores.py` — 11): первый магазин — аккаунт; новый магазин — свой ключ, загрузка в очереди, товары,

кабинета (тот же кабинет — второй ключ можно, другой — 409, уже подключённый — 409 / 400, название по ключу); пустой магазин
меняет кабинет; переименование, дубль названия, первый не отключить, отключённый — 404 и без синхронизации, возврат, чужой
PATCH — 404; закрытый аккаунт останавливает все магазины; токен на id магазина — 401, `admin users`; журнал — по магазину;
Telegram владельца — название магазина и `store=` в ссылке, счётчики на странице, «последнее отправленное»; `admin resync`.
`test_sync_products` — архив товаров не из кабинета и возврат. Миграция 0032 на Postgres с данными «три кабинета у одного

## 10.2 — Кнопка «Синхронизация» в шапке (22.10.2026)

Миграций нет. Вместо «Обновлено N минут назад / Обновить сейчас» (только товары, шаг 1.2) — кнопка «Синхронизация» по всем
видам данных текущего магазина (правило 17).

**Причина провала** — `run.stats["error_kind"]` (`services/sync/runner.py`, `error_kind`): `no_key`, `key`, `key_role`
(у ключа нет роли или 403), `rate_limit`, `ozon_down` (5xx, тайм-аут, нет связи), `ozon_rejected`, `bank_token`,
`bank_down`, `bank_rejected`, `internal`, `interrupted` (зависший запуск), `queue` (брокер недоступен). Текст ошибки — в
`run.error`, как раньше (ключ и токен клиенты вырезают). У старых запусков причина — по тексту (`overview.classify`).

**Обзор** — `services/sync/overview.py`: виды `products`, `stocks`, `promotions`, `finance`, `balance`, `postings` (если
у магазина был ключ Ozon; ключ истёк — у каждого вида «Ключ Ozon не подключён или истёк» и «Подключить ключ», обновить
нельзя) и `bank` (если подключён; все банки ждут новый токен — «Заменить токен», один из нескольких — ошибка, но
обновляется). Состояние вида: идёт загрузка → ошибка → ещё не загружались → давно (старше двух интервалов расписания
`SCHEDULE`) → свежие. `PROBLEMS` — что случилось простыми словами, что сделать и куда перейти. `RECENT` — вручную не чаще:
товары, остатки, банк — 10 мин, акции — 15, начисления и баланс — 30, отправления — 60. Общее: running → error → stale →
fresh, нечего загружать (ключа не было, банка нет) — `no_source`, не ошибка: можно работать на отчётах XLSX. Самые
старые данные — вид, который ещё не загружался (идущая первая загрузка — после остальных), или с самым давним обновлением.

**API.** `GET /sync/status` — прежние поля (страницы разделов) и новые: `state`, `oldest_kind`, `oldest_success_at`,

загружаются: …. Обновлены недавно: … — снова можно через N мин.»). Неизвестный вид, вид без ключа или банка — 400. Ключа
