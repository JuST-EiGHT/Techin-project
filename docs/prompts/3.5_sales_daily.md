Шаг 3.5 — продажи по товарам по дням (принципы — docs/DATA_HISTORY.md).

Это основа для дней запаса (шаг 1.3 сейчас показывает «нет данных»), страницы товаров
(4.1: дата последней продажи), поставок (5.2) и аномалий (7.1).

1. Таблица sales_daily: user_id, date, offer_id / product_id, sku, qty_sold, qty_returned,
   revenue, source (api | xlsx), calculated_at. Производная: пересобирается из начислений,
   руками не правится.
2. Источник — начисления (accruals) «Выручка» и «Возврат выручки» по SKU: из API они есть
   с 2022 года, плюс загруженные XLSX. Аналитику Ozon (/v1/analytics/data) не используем как
   основу — она хранит только 3 месяца. Если для поставок нужна дата заказа или склад/кластер
   отправления — сверить с документацией отправлений FBO (docs/ozon/) и согласовать с владельцем.
3. Пересборка за затронутые дни — после синхронизации финансов и после загрузки отчёта.
4. День без загруженных начислений (нет в accrual_days) — «нет данных», а не 0 продаж.
5. Подключить services/stocks.avg_daily_sales: продажи за 30 дней / 30 (по товару; по складам —
   если в данных Ozon есть склад отправления).
6. GET /api/v1/sales/daily (product_id, date_from, date_to) — для графиков.
7. Тесты: пересборка после повторной синхронизации, возвраты, пропущенные дни, дни запаса.

Готово в 3.2–3.4 — переиспользовать: строки начислений по дням с выбором источника (`services/pnl_data.coverage`,
`load_lines`: день, тип, сумма, штуки, артикул, отправление), группы типов и отнесение к товару по отправлению
(`engine/product_pnl.group_of`, `services/product_pnl._posting_offers`); пропуски — `Coverage.missing` (нет данных ≠ 0).
